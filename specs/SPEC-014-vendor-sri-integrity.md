# SPEC-014: SRI-хэши для vendored UI

| Поле | Значение |
|---|---|
| **Приоритет** | 🟢 Низкий |
| **Категория** | Security / supply chain |
| **Файлы** | `scripts/vendor-ui.mjs`, `src/dashboard/vendor.ts`, `src/dashboard/fragments.ts` |
| **Связь с аудитом** | пункт 5.4 |
| **Объём работ** | 2-3 часа |
| **Breaking change** | Нет (additive — integrity атрибуты) |

## Проблема

`scripts/vendor-ui.mjs` (942 байта на 200 KB vendored ассетов) скачивает UI-библиотеки (htmx, css, fonts) и инлайнит их в `src/dashboard/vendor.ts`. HTML-шаблоны в `src/dashboard/fragments.ts` ссылаются на эти inline-ассеты через `<script>` без `integrity` атрибута.

### Что это значит

Если кто-то получит write-доступ к репозиторию (через PR, через dependency confusion, через cache poisoning), он может подменить содержимое `vendor.ts` на вредоносный JS. Браузер пользователя дашборда выполнит его как same-origin script.

> В текущей реализации это self-hosted dashboard на loopback (127.0.0.1), поэтому attack surface ограничен. Тем не менее SRI — best practice, особенно если `HOST=0.0.0.0` (см. warning в `src/node.ts:1264`).

## Требования

1. При скачивании каждого UI asset'а в `scripts/vendor-ui.mjs` считать SHA-384 хеш payload.
2. Сохранять хеш в манифест (например, `assets/integrity.json` или inline в `vendor.ts`).
3. При рендеринге HTML в `src/dashboard/fragments.ts` добавлять `integrity="sha384-..."` к `<script>` и `<link rel="stylesheet">`.
4. Self-integrity: дашборд подписан против tamper'а bundle тем же путём (опционально).

## Дизайн

### scripts/vendor-ui.mjs (обновление)

```js
import { createHash } from 'node:crypto';
import { writeFile, mkdir } from 'node:fs/promises';
import { join } from 'node:path';

const ASSETS = [
  { url: 'https://unpkg.com/htmx.org@1.9.10/dist/htmx.min.js', name: 'htmx.min.js' },
  { url: 'https://unpkg.com/htmx.org@1.9.10/dist/ext/sse.js', name: 'htmx-sse.js' },
];

function sha384Base64(buf) {
  return 'sha384-' + createHash('sha384').update(buf).digest('base64');
}

const out = {};
const integrity = {};

for (const { url, name } of ASSETS) {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`Failed to fetch ${url}: ${res.status}`);
  const text = await res.text();
  out[name] = text;
  integrity[name] = sha384Base64(Buffer.from(text, 'utf8'));
}

await mkdir('src/dashboard', { recursive: true });
await writeFile('src/dashboard/vendor.ts',
  `// Generated by scripts/vendor-ui.mjs. DO NOT EDIT.\n` +
  Object.entries(out)
    .map(([name, content]) =>
      `export const ${name.replace(/[^A-Za-z0-9]/g, '_').toUpperCase()}_JS = ${JSON.stringify(content)};`)
    .join('\n') + '\n' +
  `export const INTEGRITY = ${JSON.stringify(integrity, null, 2)} as const;\n`
);
```

### src/dashboard/fragments.ts (обновление)

```ts
import { INTEGRITY } from './vendor.js';

// В renderFragment функциях:
const htmxScript = `<script src="/static/htmx.min.js" integrity="${INTEGRITY['htmx.min.js']}" crossorigin="anonymous"></script>`;
```

> ⚠️ Если ассеты инлайнятся напрямую (не через `<script src=>`), SRI бесполезен (SRI только для подгружаемых ресурсов). В текущей реализации (`src/dashboard/vendor.ts` имеет JS-строки inline) — SRI не поможет. Нужно либо **перейти на `<script src=>`**, либо использовать **CSP hash directive**.

### Альтернатива: CSP hash

```ts
const CSP_SCRIPT_HASHES = computeSha384Hashes([HTMX_JS, HTMX_SSE_JS]);

// В ответе дашборда:
res.setHeader('Content-Security-Policy',
  `script-src 'self' ${CSP_SCRIPT_HASHES.map(h => `'sha384-${h}'`).join(' ')}`);
```

Это **эффективнее** SRI для inline-скриптов. CSP hash имеет тот же эффект tamper-resistance без необходимости external src.

## Тесты

### tests/vendor-integrity.test.ts (новый)

```ts
import { describe, expect, it } from 'vitest';
import { createHash } from 'node:crypto';

describe('Vendor integrity', () => {
  it('INTEGRITY contains sha384 hashes for all assets', async () => {
    const { INTEGRITY } = await import('../src/dashboard/vendor.js');
    expect(INTEGRITY).toBeDefined();
    for (const [name, hash] of Object.entries(INTEGRITY)) {
      expect(hash).toMatch(/^sha384-[A-Za-z0-9+/=]+$/);
      // Verify hash matches file content.
      const content = await getContentByName(name);
      const computed = 'sha384-' + createHash('sha384').update(content).digest('base64');
      expect(hash).toBe(computed);
    }
  });

  it('dashboard response includes Content-Security-Policy header', async () => {
    // Запустить dashboard mini-server, проверить заголовки.
    const res = await fetch('http://127.0.0.1:<port>/');
    const csp = res.headers.get('content-security-policy');
    expect(csp).toMatch(/script-src/);
    expect(csp).toMatch(/sha384-[A-Za-z0-9+/=]+/);
  });
});
```

## Обратная совместимость

- CSP — additive (если CSP задан, браузеры без поддержки CSP игнорируют).
- SRI — additive (если integrity задан, браузер проверяет; несоответствие = блок).
- Никаких изменений runtime поведения для легитимных клиентов.

## Открытые вопросы

- **Q1:** CSP vs SRI? **Решение:** CSP hash для inline-скриптов (текущая модель), SRI для external `<script src=>` (будущая).
- **Q2:** Должен ли дашборд отвечать `Content-Security-Policy-Report-Only` для мониторинга, перед enforce? В dev — `Report-Only` удобнее. В production — `enforce` безопаснее.
  - **Решение:** оставить один `enforce` режим, чтобы не было дрейфа.
- **Q3:** Trusted Types? Out of scope для этой спеки.
